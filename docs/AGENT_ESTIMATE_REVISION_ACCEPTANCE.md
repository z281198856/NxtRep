# 营养重估与待确认草稿修订验收

更新日期：2026-10-11。本轮基于现有 Agent、Task State、Tool Gateway、业务 Service、确认卡和执行日志增量补强，保留现有 API 和数据库结构，没有替换 Agent 架构。

## 实际问题与修订结果

原来的餐食修订参数主要支持修改克数，无法表达“份量不变，但脂肪估高了”。因此模型即使理解了用户反馈，也没有可执行的营养重估参数。部分失败后的引导还要求重新生成餐食，与防重复记录的约束冲突，最终表现为继续追问用户、只改米饭或执行失败。

本轮让现有餐食工具支持局部重估，参数包含该份食物的热量、蛋白质、碳水、脂肪总量及估算依据。程序校验来源、数值、份量、实体和版本，沿用确认流程。用户提供“没那么油”“是带汤嫩豆腐”等有效反馈后，模型可以给出可修改的估算草稿，不再要求用户自行计算脂肪或用油克数。

同时修复了相关多轮问题：只读插问后丢失原餐任务、最近其他业务卡片抢占餐食目标、上一轮单项食物焦点污染整餐反馈、修改待确认更正卡时丢失之前的营养调整，以及读到正式记录旧份量后错误重估。

补充真实对话还发现“豆腐也改成150克，先不要确认”被当成删除请求。原因是旧的确定性路由只要看到“不要”就偏向删除，且食物短称无法匹配候选时提前进入澄清。本轮在现有状态和规划模块共用一个轻量删除意图检查：否定删除、延后确认和保留其他项不触发删除；不明确的短称继续交给现有语义路由与真实记录查询。没有新增通用 NLP 系统。

连续修改还暴露了两个参数延续缺陷：上一项食物的位置被当成不可更换的实体，以及“其他不变”等尾句让已经明确的克数被丢弃。现在同一餐明确切换食物时清理旧的食物位置，继续保留餐食 ID；唯一可匹配的单项食物和明确克数可由现有状态模块直接解析，复杂表达仍交给模型。候选食物的位置沿用读取结果的原始索引，不因待确认移除而重新编号。

## 覆盖链路

| 链路 | 当前行为 | 验证范围 |
| --- | --- | --- |
| 未确认餐食草稿 | 读取原草稿，保留日期、餐次、食物及未修改份量，局部重估后生成替代卡 | 单测、真实 PostgreSQL、真实模型/API |
| 已保存餐食 | 读取真实 entry ID 与版本，生成原餐的更正卡，确认前不改正式记录 | 单测、真实 PostgreSQL、真实模型/API |
| 待确认餐食更正卡继续修订 | 合并之前的份量、重估及移除操作；读取有效待确认预览，而非只读正式旧值 | 单测、真实 PostgreSQL、真实模型/API |
| 餐食任务中插问 | 只读查询不写数据，后续纠正可恢复原餐任务 | 单测、真实模型/API |
| 餐食照片补充反馈 | 已绑定餐食时进入既有餐食修订路径，不能绕过绑定目标另建一餐 | 脚本/单元测试；真实新照片流程未验收 |
| 个人资料待确认草稿 | 读取原草稿，只覆盖本次字段，保留此前修改 | 真实 PostgreSQL、真实模型/API |
| 自定义食品待确认创建或修改 | 保留原食品字段；不再把未保存食品当成已有 food ID；修改参考克数时对未指定营养值换算一次 | 真实 PostgreSQL；创建草稿自然语言修订另有真实模型/API |
| 身体测量待确认草稿 | 局部修订体重等实测值，保留未修改的围度、日期；没有真实确认卡不能宣称完成 | 真实 PostgreSQL、真实模型/API |
| 营养目标待确认草稿 | 从现有目标草稿修订，保留其他目标，检查生效版本是否已变化 | 真实 PostgreSQL、真实模型/API |
| 训练计划待确认草稿 | 读取原计划后修订；保留未修改的训练日及动作，继续使用现有计划校验 | 真实 PostgreSQL、真实模型/API；真实模型用例为计划名称修改 |
| 训练记录、日历、取消及撤销 | 保留既有专用工具与确认流程，本轮没有重写这些已支持的链路 | 后端全量回归；不宣称本轮逐项做过设备验收 |

其他业务草稿使用一个受任务类型限制的辅助工具层 `read_pending_business_draft` / `propose_pending_draft_revision`，调用原业务 Schema 和 Service。工具网关阻止在修订同一待确认草稿时另建独立草稿，沿用现有幂等日志及恢复机制。原卡和新卡在同一事务中建立替代关系；新草稿校验失败时保留原卡。

## 执行边界

- 用户说“脂肪偏高”，指向当前餐食估算时，可以按食材和做法重新估算；问“为什么脂肪高”、查询今日摄入或讨论目标时，不应自动修改餐食。
- 营养重估只调整餐内未经核实的模型/视觉估算。不能为了达到目标擅自改掉已经吃下的克数，也不能直接改写食品库版本或已核实的营养数据。
- 份量修改和营养重估可以先后发生，前一次修改必须保留；后续按克数缩放只执行一次。返回的食物位置仍使用原记录的稳定索引，不能因移除前一项而串项。
- 新卡需用户确认后生效，旧卡不再可批准。已保存餐食确认后仍是同一个 entry，保留修订历史，不新增一顿午饭。相同确认请求重放返回已有结果。
- 版本变化、卡片过期、食物来源不允许重估、目标不唯一等情况返回具体原因或要求选择，不把它们统一显示为“评估失败”。
- 身体测量、训练重量、组数、次数等需要实测的数据仍应补充真实参数，不能套用饮食估算政策。

## 在 App 里验收

当前本地 API 与 Android App 已更新并打开。建议用专门的测试记录；点击确认会修改正式业务数据。

1. 在原午饭会话发送：“脂肪偏高了，我觉得不是很油，所有份量不变，请按清淡做法重新估算。”应出现更新的待确认卡，保留食物和克数，显示营养估算及依据；不应要求你计算油或脂肪克数。如果原卡已过期、已关闭或使用已核实食品数据，应明确说明原因。
2. 暂不确认，说：“米饭改成150克，其他不变。”新卡应保留刚才对菜品的营养重估，只更新米饭份量。旧卡不能再批准。
3. 反向验证：继续把某个模型估算菜品改成150克，再说：“这个菜的脂肪还是估高了，实际没那么油，份量按上一张卡保持不变。”该菜应仍是150克，米饭及其他菜不变；不得恢复成正式记录中的旧份量。
4. 插问：“为什么这样估算？先不要改。”应只解释，不新建确认卡。再明确纠正某项菜品，应回到同一餐。
5. 确认最新卡，去饮食记录检查午饭数量。再说：“刚才那餐的豆腐其实是带汤嫩豆腐，蛋白质可能估高了，其他不变。”应是原餐的更正卡；确认后仍只有原来那顿午饭，其他份量不变。
6. 验证资料等草稿时，先生成待确认卡，暂不确认，再按下表纠正。检查未提到的字段保留、旧卡失效、正式记录确认前不变。

| 草稿类型 | 可测试的后续输入 | 应检查 |
| --- | --- | --- |
| 资料 | “身高改成176厘米，训练天数不变。” | 保留原草稿的训练天数及其他资料修改 |
| 自定义食品 | “脂肪改成3克，其他营养和参考份量不变。” | 修改原食品草稿，不能转成长记忆或要求不存在的食品 ID |
| 测量 | “体重其实是69公斤，腰围不变。” | 保留腰围和日期，不再创建另一份独立测量草稿 |
| 营养目标 | “脂肪上限改成60克，其他不变。” | 热量、蛋白质、碳水及生效日期保留 |
| 计划 | “名称改成上肢训练，其他安排不变。” | 保留原训练日、动作和组次，确认前不替换生效计划 |

## 仍保留的限制

营养数字是带依据和不确定性的估算，不能视为实验室测量或包装标签核验。多个餐食或食物无法唯一定位时仍需澄清。计划嵌套列表修改沿用现有完整列表输入，模型应先读取并保留未修改部分；复杂跨多条记录操作没有在本轮扩大为通用批处理系统。没有增加开机服务，没有提交、推送或部署。
