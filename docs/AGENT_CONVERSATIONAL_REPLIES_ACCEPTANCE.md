# 分阶段输入与自然回复验收

## 本轮问题与修订

本地真实记录中的请求为“今天练了胸先帮我创建一个训练记录我再告诉你练了什么”。
路由识别为训练记录是正确的，但后续缺项检查忽略了“稍后告诉”，直接回复
“请补充动作名称、多少公斤、做了几组、每组多少次”。

这次沿用原语义路由、Task State、训练工具和确认机制：

- 路由提取本轮明确的 `awaiting_user_details` 意愿，区分已完成训练记录与未来训练计划。
- 暂存已知内容与真实缺项，步骤为 `await_user_details`；本轮简短回应等待补充，不创建猜填的业务记录。
- 下一条明细继续同一个任务；等待标记不阻碍后续正常参数补全。
- 普通训练缺项按动作、重量、组次分步询问，不一次列出全部字段。
- 无效参数、目标歧义和已有确认卡仍走原校验流程。
- 草稿创建与修订回复精简；具体确认要求通过原卡片展示。
- 用户主动查询草稿是否生效、操作失败或存在实际风险时，仍准确说明状态。
- 状态使用自然中文，不输出 `pending` 等内部值，未询问有效期时不罗列未过期卡片的过期时间。

没有调整数据库模型、公共 API、业务 Service 或前端操作方式。完整明细不足时保留的是会话任务，
只有原工具成功返回确认卡后才称为已创建业务草稿。

## App 验收

1. 发送“今天练了胸，先帮我准备训练记录，我等下告诉你练了什么”。
   应自然回应等待内容，不立刻追问组数、重量，不出现空训练的确认卡。
2. 接着发送“杠铃卧推”，应继续原任务，只询问重量。
3. 发送“60kg”，应询问组数和每组次数；发送“四组，每组8次”后才出现待确认记录。
4. 另开对话发送“先创建一个训练计划，具体训练内容我等下再告诉你”。
   应保留计划任务等待补充，不直接生成一份默认计划，也不追问实际训练重量。
5. 发送“记录今天午饭：熟米饭200克，鸡胸肉150克”。
   应生成原有确认卡，正文提供有用结果及必要估算依据，不追加大段“还没写入正式记录、批准后才生效”等重复结尾。
6. 主动询问“这份草稿现在算正式记录吗”，应准确解释待确认状态；未点击确认前正式记录不增加。
7. 在步骤1之后发送“算了，不记了”，应取消本次收集，不继续追问或生成训练记录。
