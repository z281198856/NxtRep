## 实现范围

- 聊天更正已经入账的一餐中指定食物的克数，走 `nutrition_entry_update_draft`；
  删除一条误记餐食走 `nutrition_entry_delete_draft`。未确认草稿修订、新增餐食和食品库修改继续使用原任务。
- `read_saved_meal_for_change` 按日期、餐次、食物名、记录时间或已知记录 ID 读取本人记录。
  食物名优先精确匹配；同一天有多餐、同餐有多个同名食物时，要求选择具体记录，不任意猜选。
  用户已给出的食物/时间用于缩小候选，避免漏掉信息后重复追问。
- 必须先读取实际记录及版本，再用 `propose_saved_meal_update` / `propose_saved_meal_delete` 生成确认草稿。
  更正请求只允许指定食物位置和新克数，不能附带改名、替换食物或新增条目。
- 沿用该餐保存时的营养基准；食品库之后改名、更新营养或删除条目，不改变原记录的换算依据。
  旧版只有摄入营养合计的快照按原克数同比例换算；缺少必要数据则说明无法可靠重算，不伪装成功。
  原来源、估算可信度、其他食物、备注、餐次及时间保留。
- 确认卡显示餐次和时间、食物克数变化、热量及三种宏量营养的原/新合计。
  删除卡明确整条餐食将移出统计。确认前正式记录不变；历史对话可以恢复同一卡。
- 确认时锁定并重新加载记录，再核对版本。旧卡不能覆盖其他入口的新修改。
  更正和删除均保留 `NutritionEntryRevision`；删除为软删除，原记录仍保存在数据库中。
- 确认后饮食日/周统计使用有效记录更新；返回饮食页会读取新数据。
  复用已有审批幂等机制，同次相同参数的工具提案复用确认卡；不创建长期记忆或食品库条目。

## 诊断依据

真实接口第一次连续操作中，更正已成功，但删除时 Agent 没有把用户指定的食物名传入读取工具，
导致将两条午餐均列为候选并重复追问。已补充明确的读取要求，随后同一对话的更正/确认/删除/确认通过。

第二次测试的末尾比较暴露测试数据表示问题：新增接口返回 `+08:00`，数据库读取返回 `Z`，
两个字符串实际指向同一时间。验收种子统一从正式读取接口取基线，避免把时区表示变化误报为业务修改。

## App 人工验收

1. 在“饮食”页选择有记录的一天，确认具体餐次、食物名、克数和时间。
   若没有记录，先记录一餐并确认保存。下面日期、名称和克数必须换成自己的实际数据。
2. AI私人教练发送：“请把2026-10-07已经保存的午餐中熟米饭从200克更正为100克，鸡蛋和其他餐食不变，沿用原营养依据，先给草稿。”
   应显示“更正已保存饮食”，包括原/新克数和营养合计。确认前返回饮食页，原记录仍是200克。
3. 点“新对话”，再从“历史与记忆”打开原对话，应恢复同一卡。点“确认更正”，
   返回饮食页，熟米饭应变为100克，原鸡蛋、备注和其他餐食保留，日/周营养统计相应减少。
4. 继续发送：“请删除2026-10-07午餐中含熟米饭的那条已保存记录，这一餐是误记，其他餐食和食品库不变，先给草稿。”
   应显示“删除饮食记录”，明确删除的是整条餐食。确认前仍能看到记录；点“确认删除”后所选餐食不再出现在饮食页和摄入统计中，其他餐食仍在。
5. 再生成草稿并取消或拒绝，记录应保持原样。如果同一天有两条相同餐次和食物的记录，
   不指定时间时应要求选择；补充“12:00那条”后再生成草稿，核对没有误选。
6. “历史与记忆”中的长期记忆不应增加上述修改指令；食品库原条目不应改变。
   若草稿生成后已通过其他入口改动/删除该餐，再确认旧卡，应提示旧草稿未生效并要求重新读取。

## 边界与限制

- 本轮只更正已有食物的克数、删除一条完整误记餐食；不支持替换/新增食物、单独删除餐内一个食物、改餐次或时间。
- 原营养是估算时，更正后的营养仍是估算，不会因重新换算变成精确实测。
- 审核卡尚无逐字段编辑弹窗；数值不对时取消旧草稿，重新提出正确请求。
- 同一餐的多个旧草稿不能当作原子批量更正；确认其中一张后，其他旧版本卡需重新生成。
- 数据库保留软删除记录和修订；本轮没有新增饮食修订历史专用页面或恢复删除记录功能。
- 模型可能超时或不正确调用工具；无真实确认卡时不得声称记录已更改。
- 本地数据库、后端和模拟器按需启动；此项同步确认不需要 worker，不创建开机自启动服务。
