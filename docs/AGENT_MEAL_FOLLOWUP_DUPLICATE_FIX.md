# 确认后补充份量导致午餐重复入账修复

日期：2026-10-07。依据本机真实餐食、确认记录、幂等记录和会话定位，未修改用户已有业务数据。

## 原因与实际影响

同一对话先记录泡椒鸡胗饭，用户在19:39批准米饭200克的午餐（整餐500千卡）；
19:40补充“米饭约两百五十克”被路由为 `nutrition_record_draft`，
工具读取确认状态后仍调用 `propose_nutrition_entry`，生成另一餐；19:42批准后新增米饭250克午餐（565千卡）。
两条的餐次和进食时间相同，创建和批准操作不同，不是同一次确认重复执行，也不是验收账户残留。

此前会话上下文只有聊天文本。第一条回复仍写“待确认”，但用户在App点确认的实际结果没有传给下一轮路由。
保存后的份量更正能力已存在，但这种省略“修改”二字的补充没有正确衔接已有记录。

## 修复

- 复用历史确认恢复的查询，读取与本会话关联、属于当前账户的确认卡数据库当前状态。
  忽略被替换的旧卡，按实际到期状态标记，只传最近6张餐食卡的简短信息、真实记录ID及食物预览。
- 当前状态优先于旧回复的“待确认”。补充原餐份量：未确认时修订原草稿；已批准时读取原记录和最新版本，生成份量更正卡。
- 路由与执行提示均禁止把已保存一餐的补充份量重新当作新增餐食；营养反馈的本地快捷分支同样区分确认状态。
- 明确另吃一餐、另一日期/餐次或再次食用仍可新增；指代不明确时核对具体餐食。
- 食物名称来自已有营养预览，避免食品库引用请求中的空名称丢失定位信息。
- 未自动删除或合并现有两条记录。原记录和统计保留，业务删除仍由用户确认。

## App验收

1. 新建一餐米饭200克及其他食物，确认保存。
2. 在同一对话只发送“米饭约两百五十克”，应显示“更正已保存饮食”，不是新增饮食卡。
3. 确认前饮食页仍是200克；确认后变成250克，餐食数量不增加、其他食物保持原样。
4. 尚未确认首次记餐时发同一句话，应修订草稿并使旧卡失效，批准后仅入账一次。
5. 明确说“晚饭也吃了，这是另外一餐，先给草稿”，应正常生成晚餐新增卡。

对于已经重复的现有午餐，核对后在饮食页删除整餐500千卡、米饭200克的旧条目，保留565千卡、米饭250克的条目。
不要只改旧条目的克数，否则两条餐食仍会计入统计。
