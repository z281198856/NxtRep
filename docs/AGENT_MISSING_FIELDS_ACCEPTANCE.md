# Agent 缺参误拦截修复验收（2026-10-10）

本轮沿用现有路由、结构化任务状态、业务工具与确认卡。没有更换 Agent 架构，没有新增数据库迁移或前端协议。

## 根因与修改

- `TaskActionHandler` 原先在判断自己是否负责某任务前，就统一拦截 `missing_fields`，导致营养目标草稿及部分个人计算没有机会读取已保存资料。现在仅对它负责的确定性业务操作做这一检查，保留跨任务的取消和确认卡恢复能力。
- 新建餐食的份量与营养缺口被误当成必须向用户询问的执行参数。现在食物已明确时，允许估算常见份量后生成草稿；处理 `amount_g`、`items[].amount_g` 及数字索引形式，并重新检查旧会话遗留缺项。
- 顶层“一盒”等量词或未知克数原先被数值清洗当作非法。保留原始输入提示，在新餐、新食品及普通食品知识咨询的估算范围内处理；具体工具调用仍须提供合法数值。
- 同样的估算策略覆盖明确新增自定义食品，以及普通食物营养咨询的 General / Knowledge 分支。读取个人数据、修改或删除既存数据不放宽。
- 显式非法数字与普通缺失分开保存。负数、零、布尔值及非有限数不会被自动替换成估算；跨轮保留错误，收到有效修正才解除。新餐收到明确量词修正时可继续估算。
- 缺参规范化后同步更新 collecting / ready；缺项数量保持在状态上限内，避免下一轮整个状态因校验失败而丢失。
- 未知食物或非法份量使用具体中文提问，路由与执行 Prompt 明确区分提取原始描述和估算。
- 真实模型复测发现，米饭本来已是200克，再说“改成200克”仍可能调用新建工具，生成独立的第二张卡，且回复错误地声称旧卡失效。现在工具入口禁止绑定原餐的任务另建餐食；明确的新任务仍可正常创建。
- 明确的单项克数修改读取真实待确认卡和版本，使用预览中的食物名称定位真实索引。同克数返回原卡，不重新估算或新建；不同克数复用现有 revision，保留原估算说明，替换并作废旧卡。
- 份量来自本轮完整修改表达，不受路由使用顶层参数或 `items` 格式影响，不沿用旧克数、旧索引。目标有歧义、否定表达、营养字段更正或同一食物同时要求修改与保留时，不执行份量变更。多项或其他字段修改仍交现有规划和修订链路处理。

## 保留的业务边界

- 不知道食物是什么、对象不唯一、伤病安全条件不明确时仍需必要澄清。
- 训练实际重量、组数、次数不能估造；个人计算不能虚构身体数值。
- 待确认餐食修订继续读取原卡并使用 revision；已保存餐食继续读取真实记录、校验版本并生成修改或撤销卡。
- 食品库修改、删除不适用新增食品的估算放行。
- 草稿必须经过既有工具、业务校验及用户确认才能写入正式数据。

## App 验收方法

1. 进入原来被卡住的午饭会话，发送“按常见单人份估算这顿午饭，先生成草稿”。应能使用前面的食物描述生成待确认卡，不再强制补克数。
2. 新建会话，输入“帮我记录午饭：番茄炒蛋、清炒西兰花和一碗米饭”。应保留全部食物，给出暂定克数及估算说明。
3. 不确认，查看卡中米饭克数，再要求改成相同克数。应说明已经是该份量，继续使用原卡，不能生成第二张独立草稿。然后改成另一个有效克数，应替换原待确认卡；其他食物不变，正式记录还未增加。
4. 核对后只确认当前有效卡，查看饮食记录，只有这一顿。再修改某项时应修改原记录，不新增同餐。旧的替代卡不能再次生效。
5. 新会话仅说“帮我记录午饭”。应询问吃了什么，不能凭空生成食物。
6. 询问“一份番茄炒蛋大概多少热量”，或要求“食品库新增番茄炒蛋，先按常见份量估算”。应分别得到有份量假设的咨询回复或食品草稿；咨询不写记录。
7. 资料已保存时请求营养目标草稿或个人计算，不应重复询问已有资料；真正缺失的计算必要数值及安全条件仍会询问。
8. 对待确认草稿说“米饭改成250克，米饭不变”，应先澄清矛盾；“米饭不要改成250克”不能直接执行份量修改。输入负数等非法克数时不能自动换成估算数字。

估算仍受食物配方、份量、用油和模型判断影响，不能视为实测营养。真实模型验收是一条连续场景的成功证据，不是所有自然表达的统计质量保证。
