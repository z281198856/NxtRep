> 范围：只处理图片，不处理视频。对用户只提供一个通用健身 Agent；训练、饮食和身体评估是内部工作流，不拆成多个 Agent。

## 1. 总体结构

```text
通用健身 Agent（LangChain + LangGraph）
  -> 多标签意图/附件分配
     -> 普通问答 + RAG
     -> 训练计划工作流
     -> 食物图片工作流
     -> 身体图片工作流
  -> 并行结果汇总 -> 安全校验 -> 草稿/确认 -> 保存结果
```

- DeepSeek `deepseek-v4-flash`：默认文本推理、对话和工具选择。
- GLM `glm-5.1`：可切换的文本模型。
- GLM `glm-4.6v-flash`：食物和身体图片理解。
- 外层用 LangGraph 管理状态和固定流程；开放式问答再使用 ReAct。
- 同进程服务调用优先；只有需要模型动态选择的能力才封装成 Tool。

## 2. 模块开发顺序

### M1 模型网关

- 统一 `TextModelGateway` 和 `VisionModelGateway`，业务代码不直接依赖厂商 SDK。
- 配置超时、重试、结构化输出、模型版本和调用审计。
- 图片模型只输出“识别候选、份量区间、置信度”，不能直接修改业务数据。

### M2 图片与 OSS

- 使用阿里云 OSS 私有 Bucket，客户端通过短时效 V4 签名 URL 直传。
- 通用接口：`POST /media/images/upload-intents`、`POST /media/images/{id}:complete`、`DELETE /media/images/{id}`。
- 只允许 JPEG、PNG、WebP；HEIC 在服务端转为 JPEG。限制大小、校验文件头、去除 EXIF。
- 数据库存 `object_key`，不存公开 URL；模型读取时临时生成 GET 签名 URL。
- 生产使用 RAM Role/STS，AccessKey 不写入代码或日志。

### M3 Agent 会话与上下文

- 会话消息支持 `attachment_ids`，图片仍从聊天界面发送。
- LangGraph 状态保存用户意图、附件、当前草稿、确认状态和错误信息。
- 上下文只加载：最近消息、会话摘要、当前任务数据、当前有效 Memory、必要 RAG 片段。

### M4 意图路由与后端调用

- 路由使用多标签结果，同时识别普通问答、训练计划、饮食图片、身体图片和数据查询；一次请求可以执行多个分支。
- 混合图片按任务分配，同一 `chat_attachment` 可以进入一个或多个只读分析分支，不因 purpose 不同而直接拒绝请求。
- 鉴权、图片校验、视觉调用、营养计算、草稿保存和确认属于 Graph 节点/Service，不做 Tool。
- 建议 Tool：`read_profile_summary`、`read_recent_workouts`、`search_exercises`、`read_daily_nutrition_summary`、`read_body_progress_summary`、`retrieve_knowledge`。

### M5 一日三餐图片记录

三餐页面先完成 OSS 图片上传，再调用饮食模块接口；聊天 Agent 则在内部直接复用相同 Service：

```http
POST /nutrition/entry-drafts:estimate-image
```

```json
{
  "image_asset_id": "uuid",
  "meal_type": "lunch",
  "eaten_at": "2026-08-28T12:30:00+08:00",
  "notes": "米饭大约一碗"
}
```

处理流程：

```text
校验图片归属 -> GLM 识别食物和估计份量
-> 匹配食品库 -> NutritionService 确定性计算
-> 返回饮食草稿 -> 用户修正/确认 -> 保存正式记录
```

返回草稿应包含食物候选、估计重量/区间、热量、蛋白质、碳水、脂肪、置信度、假设和待追问项。照片无法准确判断油量和重量，因此结果必须可编辑，不能自动写入正式记录。

### M6 身体图片评估

- 聊天附件直接进入 `body_image_workflow`，不新增 `/body/photos/uploads`。
- 身体图片可以和食物图片一起发送；两个工作流分别结构化分析，再由 Agent 汇总回答。
- 一次性评估只保存为聊天结果；提示拍摄角度、光线等误差，不做医疗诊断。
- 只有用户确认“保存为进度照”时，才建立身体领域记录，用于前后比较、列表和独立删除。

### M7 训练计划工作流

- 根据档案、目标、器械、伤痛限制和近期训练生成 `PlanDraft`。
- 先进行规则校验，再让用户确认，确认后才生成正式计划版本。
- 它是通用 Agent 内部工作流，不是独立 Agent。

### M8 RAG

- 资料：审核过的动作教学、安全提示、训练原则、营养知识和产品帮助。
- 获取：官方指南、许可开放数据和人工编写内容；登记来源、版本、授权与审核状态。
- 流程：清洗 -> 语义切块 -> embedding -> PostgreSQL FTS + pgvector 混合检索 -> 重排 -> 引用。
- 用户训练、饮食、身体数据走结构化查询，不放入 RAG。
- M8.1基础设施：GLM `embedding-3`、1024维、每批最多64条，拒绝维度错误和非有限值；
  数据量较小时先使用精确向量搜索，不提前创建HNSW。
- M8.2存储模型：`knowledge_sources -> knowledge_documents -> knowledge_chunks ->
  knowledge_embeddings`。来源只在导入完成后才能激活，文档保留不可覆盖的来源版本，文本块使用应用层
  中文分词文本生成PostgreSQL `tsvector`，向量固定为1024维；删除来源时下级记录级联删除，但业务默认停用。

### M9 Memory 与高级上下文

- 短期：最近消息 + LangGraph checkpoint。
- 中期：按消息 ID 增量生成会话摘要，保留未解决任务和确认状态。
- 长期：自动保存明确且稳定的目标、器械、伤痛限制、过敏和偏好；支持直接查看、修改和软删除，不弹确认卡片。
- 自动写入排除临时状态、假设、否定事实和第三方信息；不确定时先追问。修改和删除使用版本号防止覆盖并发变更。
- 每次按意图动态装配上下文，避免把完整历史都发送给模型。

### M10 安全、评测与上线

- 训练计划、饮食记录、营养目标和身体测量等正式业务写入经过 Draft + Confirmation。
- Memory 直接写入是受限例外，仍需用户隔离、重复抑制、版本校验、软删除和结果告知。
- 建立图片隐私、跨用户隔离、提示注入、营养估算误差、模型超时和结构化输出测试。
- 固定评测集覆盖通用问答、结构化查询、训练计划、身体测量、Memory、食物图片、
  身体图片和混合图片；真实图片通过本地 fixture key 映射，不写入仓库。
- 运行日志只记录 run、节点、状态、错误码和耗时，不记录消息正文、图片或隐式推理。
- RAG 固定评测模板已覆盖来源召回、引用正确性、无证据回答和提示注入，并已使用首批正式
  来源键；实际发布版本均为 `@1`，真实端到端评测已于 2026-09-11 以 100% 通过率完成。
