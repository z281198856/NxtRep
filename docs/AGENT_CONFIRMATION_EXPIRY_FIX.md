# 饮食日期确认卡过期恢复

日期：2026-10-14。

## 本次实际原因

日志中批准请求返回409，关联的是2026-10-12 19:17（北京时间）生成的日期更正卡，24小时有效期到2026-10-13 19:17。10月14日验收时它确实已过期。该卡没有执行时间，两餐仍在10月11日，版本仍为1。

同时存在两处缺陷：

1. 批准失败会回滚事务，事务内刚写入的expired状态也回滚。单卡GET以前没有执行列表接口已有的过期处理，仍返回pending，App因此保留可重复点击的旧卡。
2. 用户再次更正时，日期工具把过期卡当成待修订的活跃卡传给Service，Service正确拒绝过期卡，但调用链没有转入重新核对、生成新提案的路径。

## 修复范围

- 复用确认Repository已有的过期更新逻辑，让单卡查询与列表查询一致。更新按用户及卡ID限定，以SQL条件原子更新；只有pending且到期的卡改变一次状态/版本，不影响已成功或其他账号的卡。
- 已过期状态优先返回准确的过期冲突原因。
- 日期更正工具允许在原卡已过期后重新读取原记录及最新版本，并创建新的24小时待确认提案。不会延长/复活旧卡，也不会跳过确认。取消、拒绝、失败的绑定卡继续保持原来的阻断规则。
- App核实过期后移除旧卡，明确提示“已过期，未执行修改；重新提出修改并核对新草稿”。
- API、数据库模型、业务Service的正式日期执行逻辑及现有确认/幂等机制保持兼容。

- 真实本地API：一次性合成账号验收通过。旧卡批准409，GET返回expired；原对话重新生成不同ID的新卡；确认前记录未变；批准新卡并重复相同幂等请求后，原ID仅移动一次、版本只增加一次，未新增重复餐食。测试账号结束清理。

已按用户在App中再次提出的11号改10号请求生成新卡，有效期至2026-10-15 20:42（北京时间）。原11号/10号记录在生成前后完整对比一致，尚未批准用户的新卡。

## 验收步骤

1. 模拟器已停在原对话的新卡。核对源日期11号、目标10号，包含午饭和晚饭。
2. 点击新的“确认改日期”后，再去饮食页分别查看10号和11号。该次移动应保留原食物、营养和用餐时间，不新建重复餐食。
3. 测试恢复机制时，不需要等一天；专项自动化测试会把仅属于一次性测试账号的卡设置成过期。真实用户旧卡不能继续批准，需重新提出更正以取得新卡。
