# 长期记忆与食品库路由修复

日期：2026-10-06。本轮不涉及云部署、真实 iOS、提交或推送。

## 问题证据

实际请求“帮我在食品库添加自定义食品麦当劳的双层吉士汉堡和一个香芋派”，
运行 bf96e603-6361-462b-94da-7efe02b5ff46，2026-10-06 15:04:05 北京时间，
被分为 memory_write，返回 MEMORY_OPERATION_NOT_EXECUTED。工具没有执行记忆写入。
原路由把“修改信息”的对象描述得过宽；食品库已有手动创建服务，但 Agent 没有食品新增任务或工具。

## 修改

- 先按语义区分操作对象：食品、某餐、日历、测量、训练记录、正式目标、个人资料属于业务数据。
  添加、保存、修改等动词不决定记忆路由；没有对应写工具时明确能力边界。
- 保留自主记忆：稳定、属于当前用户、非假设且有持续价值的偏好、过敏、器械和习惯可以自动形成记忆。
  “我不吃香菜”可以保存；“今天不吃香菜”、他人情况、假设和一次性事件不保存。
- memory_write 在执行前再次语义复核，并提供原文证据与精简事实；证据必须来自本轮消息。
  记忆工具的权限限定在本次核实的 action/category/content，避免混合请求中的业务操作混入记忆。
  更正仍沿用版本校验；撤销允许同义表达，具体对象需匹配，不能随意删除同类的其他事实。
- 新增 food_catalog_draft 和 propose_custom_food，复用现有 Confirmation、Food、FoodVersion 与营养服务。
  用户确认 food_create 卡后才进入个人食品库，不创建餐食记录，不修改记忆。
  保存后保留来源和可信度，确认不会把估算值改成高可信度实测数据。
- 多个食品分别展示名称、基准克重与营养卡；估算说明保留。没有草稿的文字回答最多补试一次。
  同次请求的同类任务合并，同名同品牌食品重复提议时复用卡，避免重复食品草稿。

没有更改现有用户的历史记录或长期记忆。真实接口与设备验收使用自动清理的临时账号。

## App 手动验收

1. AI私人教练发送原话“帮我在食品库添加自定义食品麦当劳的双层吉士汉堡和一个香芋派”。
   应有两个食品草稿，不应显示长期记忆修改失败或保存餐食。核对克重、营养与估算说明。
2. 点击某张“确认添加”，到“饮食 → 食品库”搜索该食品。未确认的另一种食品不应进入库；
   当天已吃热量不应因食品新增而变化。
3. “我不吃香菜”：应自动形成稳定偏好，并明确告知。到 AI 页右上角“历史与记忆 → 长期记忆”核对。
4. “我今天不吃葱，明天可以吃”：仅在会话中参考，不应增加长期记忆。
5. “把自制燕麦饼加入食品库，营养先按常见配方估算；我家只有一对哑铃”：
   应有食品草稿，记忆只含器械事实，不含食品营养或新增指令。
6. “我家器械现在改成只有杠铃，没有哑铃了”：更正原器械记忆，避免同时保留冲突的旧限制。
   再发送“忘掉刚才我家只有杠铃的长期记忆，以后不要按这个器械限制训练”，应撤销对应记忆。
7. “把明天训练改到后天”“把午餐草稿的米饭减少到100克”：应走对应草稿，不应生成长期偏好。
