# Agent 自然表达与多轮操作边界验收

本轮日期：2026-10-13。围绕现有 Agent 路由、Task State、饮食日期更正排查；复用当前业务工具、确认卡、权限、版本和幂等机制。API、数据库模型和 Flutter 交互保持兼容。

## 已复现并修复的问题

| 场景 | 原因 | 本轮行为 |
| --- | --- | --- |
| “看看前天饮食多少热量”“10月10日训练做了多少组” | 知识快捷规则只看领域词和疑问词，漏掉部分日期和历史数据范围 | 回到语义路由，使用用户自己的记录查询能力 |
| “热量目标应该是2200千卡”“那个训练重量应该是55kg” | “应该”也被当成知识提问；目标、数量和指代未排除 | 判断目标设置或旧记录修改，保留必要的目标澄清和确认 |
| “鸡腿饭多少热量” | 文字食物估算进入知识检索分支 | 进入普通食物营养问答，可按合理份量估算 |
| 正在选记录时问“这个鸡胸肉多少热量？” | 候选匹配先于疑问/假设判断，可能选中并继续旧修改 | 不提前改变所选记录或参数，先处理查询，原任务可恢复 |
| 已指向历史餐食，问“这餐米饭多少热量” | 可能答通用估算，或默认读今天 | 语义路由区分实际记录查询；复用任务日期，通过现有读取工具取得原记录，已生效改期使用目标日期；用户明确说了新日期时不覆盖 |
| 查询因缺数据进入补查后重答旧任务 | 补查提示只说“原始请求”，旧任务可能混入当前回答 | 补查显式携带本轮用户原文，按当前问题补读并回答，不继续旧修改或罗列无关确认卡 |
| “如果把第二个删掉会怎样”“别改这个，先告诉我多少热量” | 指代和删除词被当作执行意图 | 交给语义路由判断咨询和否定，不自动继续旧写任务 |
| “不是55kg” | 确定性参数提取去掉“不是”后把55写成正确值 | 不把被否定的数值当成新值；明确“不对，是55”仍可补正 |
| 唯一旧候选与新对象名称不匹配 | 只有一个候选就直接使用，与用户说的对象无关 | 只有明确的通用指代可复用唯一候选；不匹配的名称需核对 |
| “帮我制定训练计划，再看看上周训练量”及类似混合请求 | 单任务快捷规则遗漏第二个请求 | 由语义 Planner 保留多个查询/操作意图 |
| “无需把11号饮食改到10号” | 日期快捷规则缺少部分否定表达 | 回到语义判断，不由快捷规则生成错误日期草稿 |
| 日期/删除确认卡后说“脂肪偏高” | 把任意餐食相关确认ID当作新餐草稿 | 识别操作类型，日期/删除卡不作为新增餐食估算草稿 |
| “午饭和晚饭改到前一天” | 餐次只能取第一个，或模型范围扩大为整天 | 从明确表达保留多个餐次，草稿仅包含这些原记录；缺一餐时先核对 |

首次29项边界回归中25项失败，证明问题存在；后续加入明确操作的正例、多餐范围及非法参数用例。边界单元测试验证“什么表达不得绕过语义路由”，真实模型评测另行验证实际分类，二者不混为一谈。

## 修改位置

- `backend/src/nxtrep_backend/agents/intent_router.py`：收紧知识、训练计划、草稿状态和餐食营养纠正的快捷路由；核对餐食确认操作类型。
- `backend/src/nxtrep_backend/services/agent_input_boundaries.py`：少量纯函数，识别需要交给现有语义路由的附加请求、疑问、假设和否定。它不负责完整意图分类。
- `backend/src/nxtrep_backend/services/agent_task_state.py`：候选选择前保护原状态，缩小唯一候选的自动匹配范围。
- `backend/src/nxtrep_backend/services/agent_handlers/general.py`：当前查询的日期引用、复用原读取工具及补查时的当前问题绑定。
- `backend/src/nxtrep_backend/services/agent_task_parameters.py`、`agent_planning.py`、`agent_handlers/meal_date_change.py`：保留明确的多餐日期修改范围，读取实际记录并校验全部餐次后生成原有日期确认卡。
- `backend/tests/test_agent_language_boundaries.py`：路由边界、状态不污染、正例与多餐范围回归。
- `backend/tests/test_agent_language_live.py`：22条合成表达的真实模型意图评测。
- `backend/tests/test_agent_language_api_live.py`：一次性测试账号的8轮真实API验收。

## 在 App 中验收

使用自己确实有记录的历史日期，先核对日历/饮食页。以下日期只是句式示例，不能替代真实存在的记录。

1. 新对话说“看看前天饮食多少热量”。应该查询前天记录，报出已记录的总量；没有记录时说明没有找到，不能泛答热量知识或编造记录。
2. 新对话说“鸡腿饭多少热量”。应该给有份量依据的估算及不确定性；不要求上传照片，不自动新增饮食记录。
3. 说“热量目标应该是2200千卡”。应该进入目标业务草稿或读取必要资料，不能把2200当长期记忆，也不能未经确认修改正式目标。
4. 在一天有多餐记录时说“把10月11日的一餐饮食改到10月10日”。当被询问餐次时，先问“这个米饭多少热量？”，应处理查询，不生成日期/份量修改。再说“继续刚才的任务”“午饭”，应恢复之前的源/目标日期，仅提出午饭的日期修改卡。
   选中午饭后再问“这餐米饭多少热量？”，应读取午饭的实际份量/营养，不能默认查今天或用常见一碗代替保存的克数。
5. 说“把10月11日午饭和晚饭改到10月10日，早餐不动”。确认卡应该只列午饭和晚饭；缺少指定餐次时应指出缺哪餐并核对。未确认前，原日期的记录保持原样。
6. 已有明确的卧推记录任务时说“不对，重量是55kg”，应修改同一目标；只说“不是55kg”时不能把55自动补成正确重量。
7. 等待选择记录时说“如果把第二个删掉会怎样？”或“别改这个，先告诉我多少热量”，应回答/澄清，不替用户选择并继续删除或修改。
8. 说“帮我制定训练计划，再看看上周训练量”，应保留计划草稿和历史训练查询两个意图，重要修改继续等待确认。

## 验证与边界

- 自动化回归：1857通过、38跳过，包含数据库测试；跳过项是需显式开启的真实模型/设备等验证。结果见 `.local/agent-language-regression.xml`。
- 真实模型意图评测：22/22通过，仅使用代码编写的合成句子和随机状态ID，不使用真实用户记录。
- 真实API：8轮通过，使用随机一次性测试账号，结束清理该账号及夹具。历史查询返回夹具正确值780千卡；查询插话后恢复并生成单餐日期卡；选定午饭后追问实际读取200克米饭的260千卡，说明改期尚未确认；多餐卡只包含午饭/晚饭。验证了生成草稿前后源日期记录完整一致、目标日期仍为空。
- 静态检查：本轮所有代码及测试文件的 Ruff 检查通过。
- 新一轮模拟器交互：尚未执行。本轮只改后端，不需要更新APK。
- 真机iOS、云部署：未执行。
- 所有可能的自然表达无法穷举。复杂否定、多对象或多操作仍可能需要澄清；是否执行和执行范围以实际读取的记录及确认卡为准。更多语义路由会增加一次模型判断的耗时；模型、数据库或外部依赖故障仍走现有错误处理。

手动回归不会自动批准草稿。本轮没有批准真实用户确认卡，没有修改真实用户饮食记录，也没有提交、推送或部署。
