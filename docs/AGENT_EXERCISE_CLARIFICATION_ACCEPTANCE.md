# 训练动作简称与候选选择修复

## 真实原因

本地原请求为“卧推55kg4组每组8次”。执行记录显示：

- 沿用了原先收集胸部训练的同一个任务。
- 正确提取55kg、4组、每组8次，未丢失日期或组次。
- 动作匹配返回杠铃卧推、上斜哑铃卧推、哑铃地板卧推、哑铃平板卧推等候选。
- 工具返回的是待澄清结果，尚未生成确认卡，也没有写入正式训练。
- 回复只展示“找到多个可能的动作，请选择具体动作”，没有具体选项。
- 结果中的 `exercise_id/exercise_name` 未被原候选适配器支持，导致结构化候选为空。
  缺项仍为 `exercise_id`，后续选择无法顺畅解除缺项。
- 真实自然描述复测还发现，从“卧推”明确成“杠铃卧推”时可能被名称变化规则误判成新动作任务。
  已将来自本轮真实候选的动作选择与新增另一动作区分，继续保留原任务和已收集参数。

上一轮真实模型验收用了明确的“杠铃卧推”，没有覆盖简称触发的这条分支。

## 最小修订

沿用现有工具、业务 Service、确认卡及会话任务，仅补齐接口之间的衔接：

1. 将真实动作和训练会话候选转成现有 `AgentTaskCandidate`。
2. 遇到动作歧义时列出真实候选名称，保留原重量、组数、次数和任务。
3. 支持名称、唯一器械简称、序号及模型理解后的真实候选ID选择。
4. 模型提出的动作ID必须属于当前已读取的候选；未知ID仍被拦截。
5. 多个哑铃变式仍不能只凭“哑铃”任选其一。
6. 对旧会话候选丢失的形态，从已保存的真实工具结果恢复候选，不要求用户重报训练详情。
7. 查询、否定、先别记录等表达仍交给语义规划；保留原有饮食错误原因和稍后确认处理。

没有修改数据库模型、公共API、业务Service或前端交互。没有为“卧推”设置自动选择杠铃的特例。

## App 验收

- 在原会话里，如果本次确实是杠铃卧推，可直接发送“杠铃的”。
  应沿用已提供的55kg、4组、每组8次生成待确认草稿，无须再报全部内容。
- 新会话发送“先准备今天的训练记录，明细等下给”，再发“卧推55kg4组每组8次”。
  应列出具体动作候选，而不是只说请选择。
- 回复“第一个”或具体动作名称，应生成相应动作的草稿，重量与组次不变。
- 回复“哑铃”但有多个哑铃变式时，应继续澄清。
- 回复“为什么选杠铃”或“先别记，先查昨天的训练”，不应直接生成训练记录。
- 确认前正式训练不新增；确认仍通过原卡片完成。
