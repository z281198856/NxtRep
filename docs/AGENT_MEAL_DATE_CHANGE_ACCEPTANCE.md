# 已保存饮食日期更正验收（2026-10-12）

## 原因与增量修复

原句“十一号的饮食记错了应该是十号的”被“饮食＋应该”的知识问答快捷规则截走；该分支没有个人饮食写工具。原有 saved-meal 更正请求也仅支持食物份量、餐内营养重估和移除食物，没有日期字段。普通问答回复之后，源日期和目标日期没有作为日期更正任务持续保存。

保留现有 API、数据库表、业务记录、工具网关和确认机制，新增一个日期专用请求与确认操作 `nutrition_entries_date_change`，支持单餐与明确的整天范围：

1. 明确的日期更正使用小范围确定性路由；其他自然表达仍使用原语义路由。
2. 当前任务保存 `action=change_date`、`source_date`、`target_date`、`scope`，沿用现有 Task State。
3. 明确日期按本地当前日期解析，不依赖模型猜月份；“前一天”相对源日期。省略年份/月时按当前年/月解释，卡片显示完整日期供核对。
4. 复用 `read_saved_meal_for_change`，整天可一次读取全部真实餐食 ID 和版本；单餐不唯一时显示餐次、时间候选。
5. 日期工具先读后提案，复用网关幂等、Trace、确认卡、安全校验和恢复机制。回复“是的”不等于选择某餐或批准写入。
6. 批准时按固定 ID 顺序锁定并校验所有记录的账户、软删除状态、版本和源日期，校验全部通过后更新原记录并写修订历史。
7. 原 ID、用餐时刻、食物与营养快照、备注保留；不删除重建、不修改食品库。目标日期原有餐食保留，两天统计自动按新日期计算。
8. 修改待确认目标日期时在同一事务中替换卡片，旧卡失效。重复批准沿用现有接口幂等与状态保护。

## App 验收方法

- 输入“十一号的饮食记错了应该是十号的”。应读取11号全部已保存餐食，生成显示 `2026-10-11 → 2026-10-10` 和每餐时间、食物的确认卡；不追问克数、热量或油量。
- 暂不确认，到饮食页查看11号和10号。记录应保持原日期。
- 在聊天中说“不对，应该是九号”。应生成新的目标为9号的卡片，原卡不可生效。
- 如确实需要移动，点击“确认改日期”。饮食页查看源日期和目标日期：仅所列餐食移动，食物、营养、时间和备注不变，其他餐食仍在。
- 单餐请求示例：“11号有一餐日期记错了，应该是10号的”。同日有多餐时应询问午饭、晚饭或全部；回答“是的”应继续保留候选，回答“午饭”或“全部”才确定范围。
- 只有原日期时，例如“十一号的饮食日期记错了”，应仅询问目标日期；后续可直接回答“九号”。
- 取消或拒绝确认卡应不改变真实记录。源记录被其他入口修改后，再批准旧卡应报冲突，整批均不移动。

## 范围与限制

- 日期更正针对已保存的一餐或明确指定的一天，不拆分单个食物到另一日，不自动合并或覆盖目标日餐食。
- 一张卡最多50餐；超过时要求缩小范围，不截取一部分后伪装整天移动。
- 不允许把已吃下的饮食移到未来日期。无记录、日期无效或目标不明确时如实说明并澄清。
- 待确认的份量或营养修改与日期调整不会偷偷合并；需先处理原待确认修改。
- Android 模拟器验收与真实 iOS 验收分开；本轮不涉及云部署和真实 iOS。
