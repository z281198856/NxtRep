# AI 回复长时间等待修复（2026-10-06）

## 实际诊断

用户发送“今天午饭是泡椒鸡胗饭”后，界面一直显示“正在制定回答思路”。
运行开始于12:54:33（北京时间），检查时已超过9分钟，状态仍为 running，
最后完成节点为 plan_request，执行分支未结束。数据库没有锁阻塞，并仍出现食品库读取。

检查当前依赖发现 LangGraph 默认递归上限为10007；项目未设置更小的工具循环上限或
工作流总时限。客户端只限制建立HTTP响应的等待时间，HTTP 200后的事件流没有进度超时；
后端每15秒发心跳，连接仍活着，用户因而一直看到转圈。

已停止卡住的后端进程，用既有 AgentRunService 关闭该次运行，恢复按需启动的后端。
没有批准、删除或修改用户的正式饮食记录。

## 修复

- ReAct 调用使用32步递归上限；达到上限返回 AGENT_STEP_LIMIT，与超时区分。
- 单次食品库检索最多尝试6次，随后明确返回检索上限与估算指引，继续创建可确认草稿。
- 文字及流式工作流总时限默认120秒，配置项为 agent_workflow_timeout_seconds。
  中间事件不延长总时限；超时取消图执行并返回 AGENT_TIMEOUT。
- 总时限发生在工具修改尚未提交时，先回滚这些修改，再记录运行失败。已提交阶段的结果
  不能被这次回滚撤销，所以错误说明要求核对草稿，不能断言所有操作都未发生。
- 非流式接口超时返回HTTP 504和契约错误；流式接口发送failed终止事件。
- 客户端150秒未收到实际SSE事件则中止连接。心跳不算回复进度；保留收到的文字、
  结束发送中状态并显示超时说明。没有自动重新发送记餐请求。

## 用户复测

在AI中说“今天午饭是泡椒鸡胗饭”，应按明确的份量假设给出营养估算和待确认卡；
没有准确食品条目时仍可生成估算草稿，不应无限换关键词。确认前饮食页不增加记录。
模型响应变慢或出错时，应结束等待并显示具体原因；重新发送前先核对待确认草稿，
避免为结果未知的请求再创建相同草稿。
